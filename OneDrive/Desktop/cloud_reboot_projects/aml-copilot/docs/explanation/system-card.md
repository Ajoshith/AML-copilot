# AI system card

A system card describes the whole deployed system: the model plus the safeguards, data and human process
around it. It follows the model-card and system-card convention (intended use, data, evaluation,
limitations). It is written to the SR 11-7 bar: someone unfamiliar with the system should be able to
understand how it works, its limitations and its key assumptions.

## System details

| | |
|---|---|
| Name | AML Investigation Co-Pilot |
| Status | Research prototype. **Not for production use** |
| Model | `claude-sonnet-5` (Anthropic) through LangChain; `openai/gpt-oss-120b` on Groq is supported |
| Reasoning | Adaptive thinking at `high` effort for all five agents |
| Prompt version | `1.2.0` in the code. The recordings behind the results below were made at `1.1.0`, before the ground-truth fix, and need re-recording |
| Policy version | `2026.09.0` (FFIEC Appendix F corpus) |
| Blueprint | *Enterprise Agentic AI Blueprint: AML Investigation*, §12 build exercise |

## Intended use

**Purpose.** Help an AML analyst investigate a transaction-monitoring alert by assembling a verified case
file: an evidence narrative, a customer-profile comparison, red-flag mapping with counter-hypotheses, and a
recommended disposition with confidence and blocking gaps.

**Intended users.** Trained AML analysts, who review and decide. Also compliance, model-risk and
engineering staff evaluating the control design.

**Decision role.** Advisory only. The recommendation is one input to a human decision. The analyst must
review the evidence, and must write an override reason whenever they disagree.

## Out of scope

- Making, filing or submitting a SAR, or any adverse action (closing accounts, blocking funds). No such
  capability exists.
- Adjudicating sanctions matches. These route to a separate sanctions team.
- Autonomous operation. Every case stops at a human.
- Use on real customer data without real identity and access management, persistent storage, and
  independent model validation.
- Generating alerts. The system investigates alerts; it does not raise them.

## How it works

Five bounded agents, each a single schema-validated call with no tools, run inside an application-owned
state machine:

| Agent | Input | Output |
|---|---|---|
| Evidence | The account's transaction timeline, analyst notes | Narrated evidence points, each cited |
| KYC/CDD | Customer profile, computed aggregates and patterns, review staleness | Expected-vs-observed comparison, risk factors, data gaps |
| Typology | Evidence, computations, FFIEC Appendix F corpus | Red-flag matches with strength; at least one counter-hypothesis; data gaps |
| Verifier | Evidence, typology assessment, computations | Per-claim checks; PASS or FAIL. Runs after a deterministic recheck |
| Coordinator | Verified evidence, KYC and typology outputs | Case memo, findings, recommendation, confidence, blocking gaps |

All numbers and the sanctions screen come from deterministic SQL, not the model. See
[Architecture](architecture.md) and [Control guarantees](controls.md).

Replayed over the eight mined cases with real recorded model output (September 2026, prompt version 1.1.0).

| Metric | Result |
|---|---|
| Labelled-laundering cases recommended for SAR consideration | 4 of 4 |
| Clean cases recommended for SAR consideration | 2 of 3 (C-006, C-008) |
| Sanctions case routed correctly | 1 of 1 |

controls hold and that measurement is wired to real ground truth. Confidence scores cluster between 0.52
and 0.62 and do not separate laundering from clean cases.

## Known limitations

1. **Ground-truth leakage.** *Both leaks fixed in code (`PROMPT_VERSION` 1.2.0); recordings pending.*
   Up to 1.1.0 the Evidence agent received each transaction's IBM `isLaundering` label, and recorded output
   cited it (C-001's memo mentions legs "flagged isLaundering true"). Agents now see transactions only
   through an explicit field allowlist (`toAgentTransaction` in `src/domain/transaction.ts`), and
   `tests/agentsWiring.test.ts` fails if any of the five agents' prompts contains the label. The
   evaluation above predates the fix and is optimistic for labelled cases until re-recorded.
   A second, indirect leak is also closed. The KYC `riskRating` used to be generated from the same label
   (every labelled-laundering account was `high`), the KYC agent read it, and recorded memos leaned on it
   ("already high-risk KYC profile"). It is now scored from static onboarding attributes only
   (`src/data/riskRating.ts`): cash-intensive, trade-based and real-estate occupations and legal entities
   score higher, and an unratable profile defaults to `high`. Among the four labelled cases the ratings are
   now medium, high, high and low; `tests/domain.test.ts` fails if the rating ever again identifies the label.
   The remaining correlation is C-004, rated `high` because its profile is empty, which is by design.
2. **Tendency to over-escalate.** Two of three clean accounts were recommended for SAR consideration,
   although the model did supply counter-hypotheses for each. Left unchecked, this pushes analysts toward
   over-filing; the override-reason requirement exists to surface that pattern.
3. **Synthetic customer context.** KYC profiles, alerts and notes are generated. Several profiles are
   deliberately implausible (for example a retail manager with a $528M expected monthly volume), which
   makes profile mismatches easier to find than in real data.
4. **Simulated transactions.** IBM AMLworld is agent-simulated. Real bank data is messier.
5. **Tiny evaluation set.** Eight cases, chosen to exercise control paths rather than to be representative.
6. **Prototype infrastructure.** Header-based identity, in-memory case state, local files for the audit log.
7. **Model dependence.** Output quality depends on the model and version. Changing either needs re-recording
   and re-evaluation. Cassette keys make that impossible to skip silently.

## Safeguards and human oversight

| Risk | Safeguard |
|---|---|
| Hallucinated facts or numbers | Mandatory citations; deterministic recomputation; fail-closed verifier |
| Invented policy | Clause IDs must exist in the FFIEC corpus |
| Confirmation bias | At least one counter-hypothesis required by schema |
| Prompt injection | No agent tools; untrusted-content wrapping; deterministic scope checks |
| Automation bias | Written override reason required when the analyst disagrees; overrides tracked |
| Unauthorised disclosure | Server-side role gates; redacted generic log |
| Irreversible action | No filing or adverse-action capability exists |

## Monitoring

Every model call is logged with model, prompt and policy versions, effort, cassette key, token usage and
latency. `GET /metrics` reports cases by state, decisions recorded and overrides. Recommended in production:
track override rate by recommendation type, verifier block rate and reasons, and SAR-consideration rate
against later outcomes.
